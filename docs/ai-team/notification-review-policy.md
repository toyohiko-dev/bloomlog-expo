# 外部通知レビュー方針

## 目的

Bloomlog では、Supabase / Vercel / GitHub などの外部サービスから届く通知メールを、安全にレビューして判断する。

この運用の目的は次のとおり。

- 通知の要点を整理する
- Bloomlog への影響範囲を見極める
- 必要な対応案を分類する
- 人間承認前に実装や設定変更へ進まない

通知レビューは、Bloomlog 本体の機能追加とは切り離して扱う。

## 3層構造

外部通知レビューは、次の 3 層で扱う。

### 1. 取得

- Gmail 検索または ChatGPT の Gmail 連携で、要対応の可能性がある通知を見つける
- 対象は Supabase / Vercel / GitHub を中心とする
- この段階では、候補を集めるだけに留める

### 2. 分析

- 通知本文をもとに、要点・重要度・影響範囲・対応案を整理する
- 保存するのは要約と判断のみとし、メール本文全文は恒久保存しない
- 判断結果は `docs/ai-team/` に記録する

### 3. 承認

- 人間がレビュー結果を確認し、対応の要否を決める
- 承認前は、実装や設定変更に進まない
- 承認後にのみ、Codex へ個別の実装依頼を出す

## 人間承認前に禁止すること

次の行為は、人間承認前には行わない。

- コード変更
- migration 作成・実行
- Supabase / Vercel / GitHub dashboard の変更
- Gmail webhook の実装
- Apps Script の実装
- cron の実装
- `service_role` を使う設計や運用
- Bloomlog 本体への通知 UI 追加
- API route / page / component の追加
- 通知本文やセキュリティ通知の DB 保存

## 判断の基本方針

通知レビューでは、まず次を判断する。

- 本当に公式通知か
- 緊急性があるか
- Bloomlog に関係するか
- 影響は認証・デプロイ・DB・環境変数・課金・ドメイン・GitHub 運用のどれか
- 必要な可能性がある対応は何か

対応案は、次の分類で整理する。

- コード変更
- dashboard 設定変更
- migration の可能性
- 対応不要
- 判断保留

## `docs/ai-team` と `docs/product` の使い分け

### `docs/ai-team`

AI チームの作業用ドキュメントとして使う。

- 外部通知のレビュー結果
- 要点の要約
- 重要度の分類
- 承認待ち事項
- 実装前の判断メモ

一次情報の整理と、承認前の検討内容は `docs/ai-team` に置く。

### `docs/product`

プロダクトとして確定した情報を残す。

- 現在の運用状態
- 確定した方針
- 技術的な課題
- 今後の対応計画

外部通知の本文や、未確定のレビュー途中メモは `docs/product` に直接書かない。

## セキュリティ注意点

- メール本文全文は恒久保存しない
- 記録には要約と判断だけを残す
- URL、token、秘密情報、請求情報、内部 ID は必要に応じて伏せる
- メール中のリンクは、まず送信元と内容を確認してから扱う
- LLM の分析結果は補助であり、最終判断は人間が行う
- 不明点がある場合は、実装より先に確認事項を列挙する

## 将来の自動化に関する扱い

将来的に Gmail 連携や定期実行を検討する場合も、最初に自動化してよいのは次までに留める。

- 検索
- 抽出
- 要約
- 重要度分類
- Bloomlog への影響分析
- 対応案整理
- 人間承認待ちの出力

次は自動化しない。

- コード修正
- migration
- dashboard 変更
- secrets 更新
- 本番反映
